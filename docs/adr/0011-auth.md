# 0011. Authentication: dashboard sessions and API keys

- Status: Accepted (revised 2026-10-04 with the implementation)
- Date: 2026-09-28

## Decision

- Passwords: argon2id, library defaults = OWASP parameters (19 MiB, t=2, p=1); 12–128 characters, no composition rules
- Unknown email and wrong password cost one argon2 verify each and return the same `auth.invalid_credentials`
- Dashboard: HS256 JWT access token (15 min, algorithm pinned on verify) returned in the body and kept in memory
  by the client; opaque refresh token `<id>.<secret>` (SHA-256 stored) in an `httpOnly`, `Secure`,
  `SameSite=Lax` cookie scoped to `Path=/v1/auth`
- Refresh tokens belong to a session (family) and rotate on every use. Marking "used" is a compare-and-set;
  presenting a used token revokes the whole session. Logout revokes the session
- API keys: `po_test_<id>_<secret>`, SHA-256 of a 32-byte secret, constant-time comparison
- **One `MerchantAuthGuard`** accepts either credential in `Authorization: Bearer` (`po_` prefix → API key,
  otherwise JWT) and yields a `Principal { organizationId, actor }`. `@Roles('owner')` + `RolesGuard` only pass
  signed-in users, so API keys can never manage API keys
- Login and refresh are rate limited (`@nestjs/throttler`, per IP, in memory per API instance)
- No Passport: a guard that accepts two credential types reads more clearly than two strategies

## Consequences

- A stolen database exposes neither usable keys, refresh tokens nor passwords
- Access tokens cannot be revoked before they expire (15 min); revoked sessions cannot refresh
- Two tabs refreshing with the same token at once log the user out (reuse detection); acceptable for the MVP
- Several API instances would need a shared (Redis) throttler storage
